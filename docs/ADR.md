# Architecture Decision Records

## 철학
MVP 속도 최우선. 작게 만들어 먼저 배포하고, 필요가 확인된 뒤에 넓힌다. 외부 의존성은 최소로 두고, 작동하는 가장 단순한 구현을 고른다.

---

### ADR-001: Next.js App Router + Vercel
**결정**: Next.js 16 App Router로 프론트엔드와 서버 로직을 한 프로젝트에 두고 Vercel에 배포한다.
**이유**: 랜딩, 대시보드, API를 한 저장소에서 다룰 수 있고 배포 설정이 거의 없다.
**트레이드오프**: 오래 걸리는 작업은 서버리스 함수의 실행 시간 제한을 받는다.

### ADR-002: Supabase로 인증과 DB 통합
**결정**: 인증과 Postgres를 Supabase 하나로 처리하고, 사용자 데이터는 RLS로 격리한다.
**이유**: 금융 데이터를 DB 수준에서 사용자별로 분리할 수 있고, 관리할 서비스가 하나로 줄어든다.
**트레이드오프**: Supabase에 종속된다. 기본 메일 발송은 발송량 제한이 있어 출시 전에 SMTP를 연결해야 한다.

### ADR-003: 이메일 + 비밀번호 로그인만
**결정**: 로그인 수단은 이메일과 비밀번호 하나만 지원한다. 가입 시 이메일 확인을 거친다.
**이유**: 외부 OAuth 앱 등록 없이 바로 구현할 수 있다.
**트레이드오프**: 소셜 로그인보다 가입 단계가 길다. 비밀번호 재설정 화면은 MVP에서 뺀다.

### ADR-004: 하이브리드 분석 + 가맹점 캐시
**결정**: LLM은 가맹점명 분류와 인사이트 문장 작성만 맡는다. 합계와 통계는 코드로 계산한다. 가맹점과 카테고리의 대응은 DB에 캐시해 같은 가맹점은 다시 호출하지 않는다. 모델은 `claude-haiku-4-5`.
**이유**: 금액이 틀릴 일이 없고, API 비용이 파일당 수십 원 이하로 유지되며 쓸수록 줄어든다. 원본 거래 행을 외부로 보내지 않아 개인정보 노출도 줄어든다.
**트레이드오프**: 낯선 파일 형식의 컬럼 해석은 코드가 감당해야 한다. 분류하지 못한 가맹점은 캐시에 남기지 않고 `기타`로 저장하며, 업로드 결과에 그 건수를 알려 준다. 같은 파일을 다시 올리면 다시 분류해 저장된 거래까지 바로잡는다. 이때 저장된 값이 `기타`인지 따로 조회하지 않고, 새 분류가 `기타`가 아닌 중복 거래를 전부 다시 쓴다 (한 번에 500건, 업로드당 최대 5,000건). 이미 캐시에 든 가맹점은 모델 ID를 상위 모델로 올려도 카테고리가 그대로이므로 Phase 2의 카테고리 수정으로 고친다.

### ADR-005: Polar 결제, 무료 + Pro 한 단계
**결정**: 결제는 Polar를 쓰고 개발은 sandbox 환경에서 한다. 요금제는 무료와 Pro 월간 구독 두 가지다.
**이유**: Polar가 판매자 역할과 세금 처리를 대행한다. 단계가 하나면 권한 체크가 단순하다.
**트레이드오프**: 해외 결제 서비스라 국내 간편결제 지원이 불확실하다. 개인 판매자 정산 가능 여부는 Phase 2 시작 전에 확인한다.

### ADR-006: 입력은 CSV와 Excel만
**결정**: CSV, `.xlsx`, `.xls`만 받는다. 속이 HTML 표이거나 탭·쉼표로 구분한 텍스트인 `.xls`도 Excel로 취급해 지원한다.
**이유**: 국내 은행·카드사가 기본으로 제공하는 형식이다. 이메일 명세서 HTML은 대부분 암호화돼 있어 서버에서 읽기 어렵다.
**트레이드오프**: 파일을 내려받지 않고 화면만 저장한 사용자는 쓸 수 없다.

### ADR-007: 무료 플랜 보관 제한은 조회 제한으로
**결정**: 무료 사용자의 데이터를 지우지 않고, 조회 시 최근 1개월로 범위만 제한한다.
**이유**: 삭제 작업이 필요 없고, Pro로 올리는 즉시 과거 내역이 열린다.
**트레이드오프**: 무료 사용자의 데이터도 계속 보관하게 된다.

### ADR-008: Vitest, 테스트는 구현 파일 옆에
**결정**: 테스트는 Vitest와 Testing Library로 쓰고 구현 파일과 같은 폴더에 둔다. 외부 서비스는 mock으로 대체한다.
**이유**: `scripts/tdd_guard.py` 훅이 같은 폴더의 테스트 파일을 기준으로 TDD 순서를 확인한다.
**트레이드오프**: 브라우저 E2E 테스트는 MVP에서 두지 않고 수동으로 확인한다.

### ADR-009: UI 라이브러리 없이 Tailwind로 직접
**결정**: 공용 컴포넌트는 Tailwind CSS로 직접 만든다. UI 컴포넌트 라이브러리는 추가하지 않는다.
**이유**: 필요한 컴포넌트가 적고, 모든 컴포넌트에 테스트를 붙이는 규칙과 잘 맞는다.
**트레이드오프**: 복잡한 컴포넌트가 필요해지면 그때 라이브러리 도입을 다시 검토한다.

### ADR-010: 가맹점 캐시는 사용자별로
**결정**: 가맹점과 카테고리의 대응은 `user_id`를 가진 테이블에 사용자별로 저장하고 RLS로 격리한다. 전체 사용자가 공유하는 캐시는 두지 않는다.
**이유**: RLS를 우회하는 서버 전용 secret key가 필요 없고, 다른 사용자의 가맹점 문자열이 한 테이블에 모이지 않는다. Phase 2의 카테고리 수정을 본인 캐시에 반영하기도 쉽다.
**트레이드오프**: 사용자마다 처음 보는 가맹점은 한 번씩 Claude를 호출한다.

### ADR-011: 무료 조회 기간은 최근 거래일 기준 1개월
**결정**: 조회 범위는 저장된 거래 중 가장 최근 날짜를 끝으로, 그 한 달 전 다음 날부터로 잡는다 (최근 거래일이 9월 13일이면 8월 14일~9월 13일). 오늘 날짜는 기준으로 쓰지 않는다. Phase 1은 이 조회 기간과 업로드 남용 방지 상한(사용자별로 최근 24시간에 20회, `uploads` 테이블로 센다)을 적용하고, 무료 플랜의 업로드 월 1회 제한은 플랜 정보가 생기는 Phase 2에서 붙인다.
**이유**: 지난달 카드 명세서처럼 오래된 파일을 올려도 대시보드가 비지 않는다. Phase 2 전에는 업그레이드 경로가 없어 업로드를 월 1회로 막으면 써 볼 수가 없다. 그래도 업로드 한 번이 Claude 요청을 최대 100건까지 일으킬 수 있어, 상한이 전혀 없으면 비용에 끝이 없다.
**트레이드오프**: 기간이 달력 월과 맞지 않아 Phase 2의 월별 추이와는 단위가 다르다. 기간의 끝이 저장된 최근 날짜에 묶여 있어 잘못된 미래 날짜 하나가 기간을 붙잡을 수 있으므로, 미래 날짜가 든 업로드는 거부한다. 최신 파일 뒤에 더 오래된 파일을 올리면 저장은 되지만 화면에 나오지 않으며, 화면이 그 사실을 알려 준다.

### ADR-012: 은행 내역은 카드 결제로 확인된 출금만 LLM에 보낸다
**결정**: 입금 행은 `수입`(카드 결제 취소는 ADR-015), 은행 내역의 출금 행 중 카드 결제로 확인되지 않은 것은 전부 `이체`로 코드에서 분류한다. 이 행들의 내용은 캐시 조회에도 Claude 호출에도 넘기지 않는다. 카드 결제로 확인되는 것은 거래구분 값에 `체크`가 든 행뿐이며, 내용 문자열로는 판정하지 않는다. 헤더에 카드 내역이라는 근거(`이용`, `승인`, `결제`, `사용`, `가맹점`)가 없는 파일은 은행 내역으로 읽는다. 카드 내역의 행과 확인된 카드 결제는 가맹점명에서 숫자 4개 이상이 든 숫자·하이픈 구간을 가린 뒤에 보낸다.
**이유**: 은행 내역의 적요에는 이체 상대방 이름과 계좌번호가 섞여 있다. 이름과 계좌번호를 LLM에 보내지 않는다는 규칙을 코드로 지킨다. 이체·송금·대체가 든 행만 막으면 은행이 `전자금융`, `모바일`, `오픈뱅킹`으로 적는 이체에서 상대방 이름이 넘어가고, `어린이체험관`이나 `서울대체육관` 같은 가맹점명은 이체로 잘못 읽힌다. 확인된 것만 내보내면 모르는 유형과 종류를 알 수 없는 파일은 기본으로 막힌다. `카드`라는 글자만으로 통과시키지 않는 것은 신용카드 대금 출금(`카드대금`)이 카드 결제가 아니기 때문이다.
**트레이드오프**: 통신비·보험료 같은 자동이체와 현금 인출도 `이체`로 묶인다. 거래구분 열이 없는 은행 파일과 체크카드 결제를 `체크`가 아닌 말로 적는 은행의 파일은 출금이 전부 `이체`라서 카테고리 분석이 비어 보인다. 헤더에 카드 낱말이 없는 카드 파일은 은행 내역으로 읽혀 결제 금액이 수입으로 잡힌다. 실제 파일에 맞춘 보강은 Phase 3에서 한다.

### ADR-013: 파일 파싱은 SheetJS, 공식 CDN tarball로 설치
**결정**: CSV, `.xlsx`, `.xls`, HTML 표를 SheetJS(`xlsx`) 하나로 읽는다. npm 레지스트리가 아니라 `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`를 버전 고정으로 설치한다. 텍스트인지 바이너리인지는 확장자가 아니라 파일의 앞쪽 바이트로 판별하고, ZIP(`.xlsx`) 입력은 SheetJS에 넘기기 전에 `node:zlib`로 압축을 푼 크기가 20MB를 넘지 않는지 확인한다. 이때 헤더에 적힌 크기가 실제로 푼 크기와 다른 파일과 ZIP64 파일은 거부하고, 항목 하나를 256KB 이상으로 센다. 시트는 이름만 먼저 읽어 20개를 넘으면 거부하고 하나씩 읽는다. 시트가 선언한 범위가 100만 칸을 넘으면 그 범위를 훑지 않고 거부한다.
**이유**: npm 레지스트리의 `xlsx`는 0.18.5에 멈춰 있고 알려진 취약점이 고쳐지지 않았다. 사용자가 올린 파일을 서버에서 읽으므로 수정된 버전을 써야 한다. 지원 형식 네 가지를 한 라이브러리로 처리할 수 있다. 은행이 탭·쉼표로 구분한 텍스트나 HTML 표를 `.xls` 이름으로 내려 주는 경우가 있어 확장자로는 형식을 알 수 없다. SheetJS는 ZIP을 전부 메모리에 푼 뒤에야 읽고, 헤더에 적힌 크기만큼 버퍼를 먼저 잡으며, 워크북이 같은 시트를 여러 번 가리키면 그 수만큼 다시 읽는다. 그래서 몇 MB짜리 파일이 수 GB를 쓰게 만들어도 스스로 막지 못한다. 시트의 범위도 실제 셀을 세지 않고 파일에 적힌 값을 그대로 돌려주므로, 셀이 두 개뿐인 수 KB짜리 파일이 170억 칸을 훑게 만들 수 있다.
**트레이드오프**: 버전을 올릴 때 URL을 직접 바꿔야 하고 `npm audit`과 자동 업데이트 도구가 새 버전을 알려 주지 않는다. 압축을 풀어 20MB를 넘는 파일, 안에 든 항목이 80개쯤을 넘는 `.xlsx`, 시트가 20개를 넘는 파일, ZIP64 파일은 읽지 않는다. 범위를 100만 칸 넘게 선언한 시트는 실제 셀이 적어도 읽지 않는다.

### ADR-014: 중복 판정 지문은 날짜·시각·내용·금액으로
**결정**: 이미 저장된 거래인지는 날짜, 시각, 내용, 금액, 종류(지출·수입), 같은 파일 안에서 같은 값이 앞에 나온 횟수로 만든 지문으로 판정한다. 시각은 파일에 있을 때만 읽어 지문에만 쓰고 DB에는 저장하지 않는다. 계좌나 카드를 구별하는 값은 지문에 넣지 않는다.
**이유**: 지문에 시각을 넣지 않으면 같은 날 같은 곳에서 같은 금액을 쓴 서로 다른 거래가 다른 파일(카드 두 장, 한 계좌를 나눠서 내려받은 두 파일)로 올라올 때 지문이 같아져 뒤의 것이 중복으로 버려진다. 계좌나 카드로 구별하려면 계좌번호·카드번호를 읽어 와야 하는데, 이 값들은 파일에서 꺼내지도 저장하지도 않는다.
**트레이드오프**: 시각이 없는 파일끼리는 위의 경우에 여전히 한 건이 버려진다. 같은 거래를 시각이 있는 파일과 없는 파일로 한 번씩 올리면 두 번 저장된다. 계좌·카드 구별은 Phase 3에서 실제 파일로 다시 검토한다.

### ADR-015: 이체는 총 지출에서 뺀다
**결정**: `이체`로 분류된 출금은 총 지출과 카테고리 차트에 넣지 않고 따로 합계를 보여 준다. 은행 내역에 입금으로 찍힌 카드 결제 취소는 수입이 아니라 음수 지출로 읽는다.
**이유**: `이체`에는 본인 계좌 사이의 이동과 카드 대금 납부가 들어 있다. 지출로 세면 카드 내역과 그 대금이 빠져나간 은행 내역을 함께 올렸을 때 같은 소비가 두 번 잡힌다. 취소된 체크카드 결제는 번 돈이 아니라 줄어든 지출이다.
**트레이드오프**: 월세나 공과금처럼 계좌 이체로 낸 실제 지출이 총 지출에서 빠진다. 총 수입에는 본인의 다른 계좌에서 들어온 이체가 여전히 들어 있다. 같은 체크카드 결제를 카드사 내역과 은행 내역으로 둘 다 올리면 두 번 잡힌다.
