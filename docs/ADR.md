# Architecture Decision Records

## 철학
MVP 속도 최우선. 작게 만들어 먼저 배포하고, 필요가 확인된 뒤에 넓힌다. 외부 의존성은 최소로 두고, 작동하는 가장 단순한 구현을 고른다.

---

### ADR-001: Next.js App Router + Vercel
**결정**: Next.js 16 App Router로 프론트엔드와 서버 로직을 한 프로젝트에 두고 Vercel에 배포한다.
**이유**: 랜딩, 대시보드, API를 한 저장소에서 다룰 수 있고 배포 설정이 거의 없다.
**트레이드오프**: 오래 걸리는 작업은 서버리스 함수의 실행 시간 제한을 받는다.

### ADR-002: Supabase로 인증과 DB 통합
**결정**: 인증과 Postgres를 Supabase 하나로 처리하고, 사용자 데이터는 RLS로 격리한다.
**이유**: 금융 데이터를 DB 수준에서 사용자별로 분리할 수 있고, 관리할 서비스가 하나로 줄어든다.
**트레이드오프**: Supabase에 종속된다. 기본 메일 발송은 발송량 제한이 있어 출시 전에 SMTP를 연결해야 한다.

### ADR-003: 이메일 + 비밀번호 로그인만
**결정**: 로그인 수단은 이메일과 비밀번호 하나만 지원한다. 가입 시 이메일 확인을 거친다.
**이유**: 외부 OAuth 앱 등록 없이 바로 구현할 수 있다.
**트레이드오프**: 소셜 로그인보다 가입 단계가 길다. 비밀번호 재설정 화면은 MVP에서 뺀다.

### ADR-004: 하이브리드 분석 + 가맹점 캐시
**결정**: LLM은 가맹점명 분류와 인사이트 문장 작성만 맡는다. 합계와 통계는 코드로 계산한다. 가맹점과 카테고리의 대응은 DB에 캐시해 같은 가맹점은 다시 호출하지 않는다. 모델은 `claude-haiku-4-5`.
**이유**: 금액이 틀릴 일이 없고, API 비용이 파일당 수십 원 이하로 유지되며 쓸수록 줄어든다. 원본 거래 행을 외부로 보내지 않아 개인정보 노출도 줄어든다.
**트레이드오프**: 낯선 파일 형식의 컬럼 해석은 코드가 감당해야 한다. 분류 품질이 부족하면 모델 ID만 바꿔 상위 모델로 올린다.

### ADR-005: Polar 결제, 무료 + Pro 한 단계
**결정**: 결제는 Polar를 쓰고 개발은 sandbox 환경에서 한다. 요금제는 무료와 Pro 월간 구독 두 가지다.
**이유**: Polar가 판매자 역할과 세금 처리를 대행한다. 단계가 하나면 권한 체크가 단순하다.
**트레이드오프**: 해외 결제 서비스라 국내 간편결제 지원이 불확실하다. 개인 판매자 정산 가능 여부는 Phase 2 시작 전에 확인한다.

### ADR-006: 입력은 CSV와 Excel만
**결정**: CSV, `.xlsx`, `.xls`만 받는다. 속이 HTML 표인 `.xls`는 Excel로 취급해 지원한다.
**이유**: 국내 은행·카드사가 기본으로 제공하는 형식이다. 이메일 명세서 HTML은 대부분 암호화돼 있어 서버에서 읽기 어렵다.
**트레이드오프**: 파일을 내려받지 않고 화면만 저장한 사용자는 쓸 수 없다.

### ADR-007: 무료 플랜 보관 제한은 조회 제한으로
**결정**: 무료 사용자의 데이터를 지우지 않고, 조회 시 최근 1개월로 범위만 제한한다.
**이유**: 삭제 작업이 필요 없고, Pro로 올리는 즉시 과거 내역이 열린다.
**트레이드오프**: 무료 사용자의 데이터도 계속 보관하게 된다.

### ADR-008: Vitest, 테스트는 구현 파일 옆에
**결정**: 테스트는 Vitest와 Testing Library로 쓰고 구현 파일과 같은 폴더에 둔다. 외부 서비스는 mock으로 대체한다.
**이유**: `scripts/tdd_guard.py` 훅이 같은 폴더의 테스트 파일을 기준으로 TDD 순서를 확인한다.
**트레이드오프**: 브라우저 E2E 테스트는 MVP에서 두지 않고 수동으로 확인한다.

### ADR-009: UI 라이브러리 없이 Tailwind로 직접
**결정**: 공용 컴포넌트는 Tailwind CSS로 직접 만든다. UI 컴포넌트 라이브러리는 추가하지 않는다.
**이유**: 필요한 컴포넌트가 적고, 모든 컴포넌트에 테스트를 붙이는 규칙과 잘 맞는다.
**트레이드오프**: 복잡한 컴포넌트가 필요해지면 그때 라이브러리 도입을 다시 검토한다.
