# architecture — 구조적 일관성

파일이 맞는 레이어에 있는지, 레이어가 제 일만 하는지, 문서에 정한 기술 선택을 벗어나지 않았는지 본다.

## 본다

- 디렉토리 구조와 레이어 책임, 서버·클라이언트 경계의 패턴, 기술 선택, phase 범위.

## 보지 않는다

- 클라이언트에서 외부 서비스를 직접 부르는 문제 → security
- 이름, 문구, UI 가이드 → conventions
- 변경이 다른 파일과 어긋나는지 → cross-file

## 읽을 문서

- `docs/ARCHITECTURE.md` 전체 (짧다)
- `docs/ADR.md`: 각 ADR의 **결정** 줄만. 변경이 닿는 ADR은 전문을 읽는다.
- `docs/PRD.md`의 `개발 단계`와 `MVP 제외 사항`
- `phases/index.json` (현재 phase 확인)

## 체크 항목

1. 파일이 맞는 곳에 있는가? 페이지와 라우트는 `src/app/`, UI는 `src/components/`, 로직은 `src/lib/`, 외부 API 래퍼는 `src/services/`, 타입은 `src/types/`, 스키마는 `supabase/migrations/`.
2. 페이지 파일이 데이터 조회와 컴포넌트 조합만 하는가? 계산이나 검증 로직이 페이지나 컴포넌트에 들어가 있지 않은가?
3. Server Component가 기본인가? `"use client"`가 인터랙션이 필요한 곳에만 붙었는가?
4. 데이터 변경을 서버 액션으로 하는가? 라우트 핸들러는 외부에서 호출되는 엔드포인트(웹훅, 파일 업로드)뿐인가?
5. 서버 코드가 Claude와 Polar를 `src/services/`의 래퍼를 거쳐서만 호출하는가?
6. 환경변수를 사용하는 시점에 읽는가? import만으로 예외가 나는 모듈 최상위 읽기가 없는가?
7. ADR의 기술 선택을 벗어났는가? 새 의존성, UI 라이브러리, 전역 상태 라이브러리, 다른 테스트 도구, 다른 패키지 매니저, npm 레지스트리의 `xlsx`.
8. 현재 phase에 없는 기능이나 MVP 제외 사항을 미리 만들었는가?
9. 한 번만 쓰이는 코드에 추상화나 설정 옵션을 얹었는가? (ADR 철학: 작동하는 가장 단순한 구현)
10. Next.js 16의 파일 규칙과 API를 따르는가? 확신이 없으면 `node_modules/next/dist/docs/`에서 해당 가이드를 확인한다.
