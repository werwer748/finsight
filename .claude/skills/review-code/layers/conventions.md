# conventions — 팀 컨벤션·네이밍

이름, 문구, 파일 배치 규칙, TypeScript 사용, UI 가이드를 본다.

## 본다

- 변경된 코드가 프로젝트의 규칙과 주변 코드의 방식을 따르는지.

## 보지 않는다

- 레이어 책임, 기술 선택 → architecture
- 테스트가 충분한지 → test-coverage

## 읽을 문서

- `CLAUDE.md` (이미 컨텍스트에 있다)
- `docs/UI_GUIDE.md`: `src/app/`이나 `src/components/`의 `.tsx`가 바뀌었을 때만 읽는다. `점검` 절을 먼저 읽고, 점검 항목이 가리키는 절(`전환 흐름`, `토큰`, `컴포넌트`, `문구`, `버튼 문구`)만 더 읽는다.

## 체크 항목

1. 이름이 하는 일을 드러내는가? 주변 코드의 이름 짓는 방식과 같은가? (파일 이름은 kebab-case)
2. UI 문구와 오류 메시지가 한국어인가?
3. 테스트가 구현 파일과 같은 폴더에 `이름.test.ts` 또는 `이름.test.tsx`로 있는가?
4. TypeScript strict를 피해 가는가? `any`, 근거 없는 `as` 단언, `@ts-ignore`, `!` 단언.
5. 쓰지 않는 import나 변수, 주변과 다른 스타일, 불필요한 주석이 남았는가?
6. 커밋 메시지가 conventional commits 형식인가? (`git log <merge-base>..HEAD --oneline`)

UI 파일이 바뀌었을 때만:

7. UI_GUIDE `점검` 절의 grep 명령을 변경된 `.tsx`에 적용한다. 걸리는 줄은 발견이다.
8. `점검` 1~6번을 확인한다.
9. `점검` 7~9번은 브라우저가 있어야 확인할 수 있다. 발견으로 올리지 말고 보고 끝에 "UI_GUIDE 점검 7~9번은 브라우저 확인 필요"라고 한 줄 적는다.
10. 토큰, 컴포넌트 variant, 버튼 문구를 새로 만들거나 바꿨는데 `docs/UI_GUIDE.md`가 같이 바뀌지 않았는가?
