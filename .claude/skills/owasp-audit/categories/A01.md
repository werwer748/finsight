# A01 Broken Access Control

출처: https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/ · 스냅샷 2026-10-08

## OWASP 요약

접근 제어는 사용자가 주어진 권한 밖에서 행동하지 못하게 하는 정책이다. 실패하면 권한 없는 정보 공개, 데이터 변조와 파괴, 허용 범위 밖의 기능 실행으로 이어진다.

흔한 형태는 기본 거부를 지키지 않는 것, URL·요청·내부 상태를 바꿔 검사를 우회하는 것, 식별자만 바꿔 남의 계정을 보거나 고치는 것, POST·PUT·DELETE에 접근 제어가 빠진 API, 권한 상승, JWT·쿠키·숨은 필드 조작, CORS 오설정, 주소를 추측해 들어가는 강제 탐색이다. 2025판은 SSRF(CWE-918)와 CSRF(CWE-352)도 이 항목에 넣는다.

예방의 핵심은 접근 제어를 공격자가 고칠 수 없는 서버 코드에서 하는 것, 공개 자원이 아니면 기본으로 거부하는 것, 한 번 구현해 여러 곳에서 다시 쓰는 것, 레코드 소유권을 모델 수준에서 강제하는 것이다.

## FinSight에서

모든 서버 진입점이 스스로 세션을 확인하는가, 사용자 데이터가 RLS와 `user_id`로 격리되는가, 무료·Pro 권한을 서버가 판정하는가, 외부 서비스 호출이 서버에만 있는가를 본다.

## 점검

### A01-1 서버 진입점의 인증 — 표 (다른 사용자의 데이터에 닿으면 🔴)

- 찾기: I1의 라우트 핸들러·페이지와 I2의 서버 액션. 보호 경로는 `src/lib/auth/routes.ts`에서 읽는다.
- 위반: 사용자 데이터를 읽거나 쓰는 페이지·핸들러·액션이 스스로 세션을 확인하지 않는다. 사용자 ID를 본문, 쿼리, 헤더에서 받는다.
- proxy의 리다이렉트만으로는 통과로 보지 않는다. Next 문서는 matcher가 제외한 경로에서는 Server Function 호출도 proxy를 거치지 않는다고 적고, 각 Server Function 안에서 인증과 권한을 확인하라고 한다 (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`의 "Good to know").

### A01-2 RLS와 `user_id` 격리 — 🔴

- 근거: CLAUDE.md CRITICAL(RLS), ADR-002, ADR-010
- 찾기: I4의 SQL 파일. 없으면 ⚪다. 파일은 Read로 읽는다.
- 위반:
  - 사용자 데이터를 담는 테이블에 RLS가 켜져 있지 않다.
  - 정책이 없거나 `auth.uid()`와 `user_id`를 비교하지 않는다. 쓰기 정책에 `with check`가 없다.
  - 조건이 `using (true)`다.
  - `anon`이나 `public`에 권한이나 정책을 준다.
  - 사용자 테이블 위에 `security definer` 함수나 `security_invoker`가 없는 뷰가 있다.

### A01-3 RLS를 우회하는 키 — 🔴

- 근거: CLAUDE.md CRITICAL(RLS), ADR-010
- 찾기: `grep -rnE "service_role|SERVICE_ROLE|SUPABASE_SECRET|sb_secret_" src supabase .env.example`. 결과가 없으면 통과다. ⚪가 아니다.
- 위반: RLS를 우회하는 키를 쓰는 코드나 환경변수가 있다. ADR이 그 사용을 허용했으면 허용한 범위 밖에서 쓰는 경우만 위반이다.

### A01-4 클라이언트의 직접 호출 — 🔴

- 근거: CLAUDE.md CRITICAL(서버 전용 호출)
- 찾기: I3의 파일과 그 파일이 import하는 모듈을 따라간다. `"use server"` 모듈에서는 멈춘다. L8로 교차 확인한다.
- 위반: 클라이언트 모듈이 `@supabase/*`, `@anthropic-ai/sdk`, Polar SDK, `@/services/*`, `@/lib/supabase/*`를 import한다. `.next/static`에서 `createBrowserClient`나 `GoTrueClient`가 잡힌다.

### A01-5 무료·Pro 권한의 서버 판정 — 🔴

- 근거: CLAUDE.md CRITICAL(권한 체크), ADR-007, ADR-011
- 찾기: I7. 없으면 ⚪다.
- 위반: 플랜을 JSX에서만 확인한다. 제한 밖의 데이터를 가져와 클라이언트로 내려보낸 뒤 화면에서 숨긴다.

### A01-6 요청 값으로 만드는 리다이렉트·콜백 URL — 표

- 찾기: `grep -rnE "redirect\(|emailRedirectTo|redirectTo|returnTo" src`
- 위반: 대상 URL을 헤더, 쿼리, 폼 값으로 만들면서 허용 목록으로 검증하지 않는다.

### A01-7 SSRF와 CORS — 표

- 찾기: `grep -rnE "fetch\(|Access-Control-Allow" src next.config.ts`. 결과가 없으면 통과다.
- 위반: 사용자가 준 URL로 서버가 요청한다. `Access-Control-Allow-Origin`에 `*`나 요청의 Origin을 그대로 돌려준다.

## 보고하지 않는다

- 클라이언트 폼이 서버 액션을 import하는 것. 번들에는 서버 코드가 들어가지 않는다.
- 가입, 로그인, 로그아웃처럼 세션 없이 불려도 되는 진입점에 세션 확인이 없는 것.
- 아직 없는 RLS와 권한 체크. 대상이 없으면 ⚪다.

## 수동 확인

- Supabase → Authentication → URL Configuration — Site URL이 운영 도메인이고 Redirect URLs에 넓은 와일드카드가 없다. A01-6의 값이 요청에서 오더라도 여기서 걸러진다.
- Supabase → SQL Editor — 실제 DB의 RLS 상태가 마이그레이션과 같다. `select relname, relrowsecurity from pg_class where relnamespace = 'public'::regnamespace and relkind = 'r';`와 `select tablename, policyname, cmd, roles, qual, with_check from pg_policies where schemaname = 'public';`로 본다.
- Supabase → Advisors → Security Advisor — 오류가 없다.
- Vercel → Settings → Environment Variables — Preview 배포가 운영 Supabase 프로젝트를 가리키지 않는다.
